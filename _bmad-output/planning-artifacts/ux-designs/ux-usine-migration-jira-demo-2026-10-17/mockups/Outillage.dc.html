Ce qu'il faut pour le faire en vrai

Quel outillage demander au client, dans quel ordre, et comment chaque brique se porte sur chaque cible.

Demandes, par ordre de priorité

  1. 1
    Compte de service Jira en lecture seule + jeton API. Indispensable pour le palier 1.
  2. 2
    Environnement d'exécution Python (VM ou Dataiku) avec accès réseau à Jira, plus un dépôt Git interne.
  3. 3
    Ordonnanceur et cible de publication (SharePoint ou partage réseau).
  4. 4
    Endpoint LLM validé par le client. Palier 2. À défaut, modèle on-prem.

Points d'attention par cible

VM Python

  • Ouvrir le flux vers Jira (proxy, certificats TLS), un miroir PyPI interne pour uv sync et l'accès GitHub au modèle spaCy fr_core_news_md, vérifier les projets visibles du compte de service, poser les secrets en variables d'environnement (AD-19, gitleaks).
  • Le code livré tourne sans adaptation : la CI le joue sous Linux et Windows (NFR-8).
  • Le lancement planifié se résume à usine rapport dans un cron, paramétré par config/*.yaml.

Dataiku

  • Chaque étape de la Chaîne devient une recette Python ; le domaine n'a aucune I/O à réécrire (AD-1, lint-imports).
  • Brancher le LLM Mesh demande un nouvel adaptateur derrière le port LLM existant, sans toucher au domaine.

Power Platform

  • Le connecteur Jira est limité sur le changelog et les volumes : garder l'extraction en Python et ne porter que la publication.
  • La Prévision ML n'a pas d'équivalent : le domaine reste en Python (AD-1).

Poste seul

  • Le palier 1 tourne sans LLM : les étapes LLM sont marquées sautee (FR-28, NFR-8).
  • La planification exige un poste allumé ; un .env par poste porte les secrets (AD-19, gitleaks).
